# Khoda AI multilingual company and LifeToy pages

Prepared September 19, 2026. This document records source and local validation;
production deployment and Google's indexing are separate acceptance steps.

## Problem and scope

The live Khoda site had one English URL in its sitemap and no localized pages.
Its metadata was indexable, but most of its content described the company
mission. The short Bearie section did not fully explain the broader LifeToy
hardware and software platform now described on LifeToy.ai.

The company homepage now directly explains Khoda AI's relationship to LifeToy,
AI toys and AI plushies while retaining its mission, vision, founder and contact
information. A separate `/lifetoy/` page explains the physical hardware,
firmware, character software, cloud, app and Studio relationship and what a
partner needs to consider before building a prototype. It is a company and
partnership page; LifeToy.ai remains the product/platform destination and hosts
the detailed toy guides.

Both pages have complete German and Simplified Chinese equivalents, matching
the languages of the LifeToy public website. German content uses natural
terms such as KI-Spielzeug, KI-Kuscheltiere and KI-Plüschtiere. Chinese content
explains AI 玩具 and 智能毛绒玩具. Visible language links preserve the current
page when changing language. Translations describe the website; they do not
claim that every toy supports every spoken language.

## Public artifacts

The canonical URLs are `https://khoda.ai/`, `/lifetoy/`, `/de/`, `/de/lifetoy/`,
`/zh/` and `/zh/lifetoy/`. All six pages contain complete initial HTML,
self-canonicals, page-specific titles/descriptions, social metadata, reciprocal
EN/DE/ZH/x-default alternates and matching sitemap alternates. The shared
Organization identity names LifeToy as a brand. Platform pages have breadcrumb
structured data. No reviews, ratings, product offers or FAQ rich-result claims
were added.

The Google verification file `google0cbd976d77731379.html` is unchanged.
`robots.txt` still allows crawling and names the public sitemap. The deployment
helper now copies 20 public assets and checks each over HTTPS after activation.
All six explicit `index.html` aliases redirect to their directory canonical,
retaining query strings. Existing unknown-page 404 and host-redirect checks
remain in the helper.

## Local validation

- `npm run build` generated six pages, built the production CSS, and passed the
  metadata, sitemap, reciprocal-language, schema, internal-link/anchor and
  deployment-coverage checks.
- Python compilation and `git diff --check` passed.
- Headless installed Chrome rendered all six pages at 390 × 844 and 1440 × 1000.
  All returned 200, had one H1, loaded their images and had no horizontal
  overflow or page JavaScript errors.
- Mobile interactions checked FAQ expansion, language switching while retaining
  the platform route, and navigation to the localized founder section.
- German mobile and English desktop screenshots were visually inspected.
  The site continues to use local fonts, WebP images and compiled CSS, with no
  client-side JavaScript required for content or navigation.

Untracked local browser evidence is under `build/seo-evidence/`. These checks
are layout and functional checks, not new Lighthouse or field performance
measurements. The earlier September 8 scores must not be presented as fresh
measurements for this revision.

## Production and search acceptance still required

1. Review the deployment helper's dry run against the actual Nginx host and
   deploy a pinned Git revision using the existing atomic-release path.
2. Verify all 20 public assets over external HTTPS and check canonical routes,
   nested index aliases, preserved query strings, host redirects and real 404s.
3. Verify the Google ownership file and the six-URL sitemap, then submit the
   sitemap and request inspection of representative EN/DE/ZH URLs in Search
   Console. Sitemap success and crawl requests do not prove indexing.
4. Check Google-selected canonicals and page indexing after processing. Compare
   relevant non-branded queries and landing pages over time, separating German,
   English and Chinese searches where the data permits.

No code change guarantees position one for a query. This release improves
crawlable language coverage and accurately explains what the company does;
search visibility also depends on Google's crawling, relevance assessments,
competition and evidence of reputation outside the site.

## Follow-up: app, marketplace and visible contact

Following the initial six-page deployment, the user requested mobile-app and
marketplace descriptions. Both page types now include concise app context and
visible App Store / Google Play coming-soon labels in all three languages.
There are no invented store URLs or release dates. The platform page describes
character discovery, voice conversations without a physical toy, and setup of
supported LifeToy hardware.

The Marketplace is explicitly described as planned: partners can present plush
toys using LifeToy technology; the intended journey is to meet a character, ask
product questions and select an offering with or without LifeToy hardware.
Digital and physical offerings, included hardware and features remain
listing-specific. Source inspection found that the managed partner storefront
currently uses Stripe test checkout, so the copy does not advertise a complete
live purchasing service. Product-aware shopping questions are a planned
experience, not a claim that the current voice demo answers a product catalog.

The contact action now visibly displays info@khoda.ai in each locale and retains
its mailto link. The public file allowlist remains unchanged at 20 artifacts.
No extra keyword pages, Product/Offer markup or purchase/store buttons were
added. Private application source was read only to check these descriptions;
none is copied into the public website.

Source boundaries reviewed: the shared app's ToyScanner LifeToyHome and
HeadlessCharacter screens, hardwareOnboarding controller, LifeToyProduct and
LifeToyStore screens, and the partner Studio SalesPageCard and
SalesPageDraftPreview. The new copy does not publish implementation details.
